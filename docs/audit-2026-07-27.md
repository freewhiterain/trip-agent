## 一、用户报告的问题

### #1 deep search 在信息冲突时不触发 ✅

**这是用户唯一给出的具体线索，确认存在。**

`subagents/base.py` 的收尾条件是「任一 provider 报 `sufficient` 就结束」。
但来源互相打架的时候，恰恰是最需要补搜的时候——冲突检测的结果算出来了，
却没有接到 deep search 的触发条件上。

修复：
- 证据冲突时进入 deep search，**首轮查询就带上冲突事实**（而不是重新泛搜）
- worker 的 policy 不允许 `deep_research` 时，把冲突显式写成 warning，
  而不是静默咽下去
- `deep_search._escalate_conflicts`：冲突强制再补搜一轮，但只追**未追过的**
  `fact_key`，避免烧光工具调用预算

`app/agents/subagents/base.py` `app/research/deep_search.py`

## 二、RAG 检索

### #2 冲突检测有两套实现 ✅

`app/rag/evidence.py` 和 `app/governance/evidence.py` 各有一套，
`deep_search.py` 里还有第三处内联逻辑。收敛为 `app/rag/evidence.py`
唯一实现，其余两处改为委托。

### #3 天气/交通证据被当作 180 天有效 ✅

`evidence_type` 的推导没有看文档 category，导致时效性极强的天气、交通
信息拿到了和景点介绍一样的有效期。改为按 category 推导。

`app/rag/evidence.py`

### #4 grounding 校验对中文完全失效 ✅

校验用 `re.findall(r"\w+")` 切词——**`\w+` 不切中文**，整个中文句子会被当成
一个 token，然后做整串子串匹配。模型只要改写语序，就会判定所有 claim
都没有依据，全部丢弃。改为 jieba 词级覆盖率。

`app/agents/subagents/base.py`

### #5 RRF 提前截断使 rerank 完全失效 ✅

混合检索里 RRF 融合后先截断再 rerank，rerank 拿到的候选集已经被砍掉了，
等于没有 rerank。同时修复：parent-doc 回溯结果缩水、回溯过程中分数丢失、
同义词扩展权重过高（扩展词和原词同权，query 被稀释）。

`app/rag/retriever.py`

### #6 BM25 检索器每请求重建 ✅

`local_knowledge` 每次调用都重新构建 BM25 索引。改为缓存。

`app/agents/workers/local_knowledge.py`

## 三、正确性 / 并发

### #7 is_mock 判定有两套互相矛盾的口径 ✅

本地 Worker 无条件写死 `True`，Supervisor 却按
`isinstance(raw_result, WorkerResult)` 推导。后者让 **subagent 路径上由本地
`mock_markdown` 支撑的结果彻底丢失披露标记**——用户看不出这条建议是假数据。

新增 `evidence_is_mock()` 作为唯一判定点，Supervisor 的 `worker_node` 与
`route_planner_node` 按证据来源兜底。

`app/rag/evidence.py` `app/agents/supervisor.py`

### #8 审批 decide 存在写覆盖竞态 ✅

原先是 `get` → 检查 status → `save` 三步。两个并发请求会双双读到 `pending`，
**后写的一方静默覆盖前一方的决定**——用户点「拒绝」，可能被同时到达的
「批准」改写，且无任何报错。

改为仓库层 `settle_once` 原子流转，Postgres 侧用条件
`UPDATE ... RETURNING`（沿用 `complete_once` 的既有写法）。

`app/governance/approvals.py` `app/governance/postgres.py`

### #9 get_llm 连接池泄漏 ✅

每次调用都新建一对**永不 close** 的 httpx 客户端，而它在每一次对话轮次都会
被调用——连接池随请求量单调增长。改为复用共享客户端，并在 `lifespan`
收尾时归还。

`app/agents/llm.py` `app/main.py`

### #10 health 路由从未注册 ✅

`app/api/v1/health.py` 一直完整实现着 `/health` 和 `/health/detail`，
却从未 `include_router`——两个端点在线上一律 404，而设计文档把
`/health/detail` 记作在用的基础设施。

### #11 进程被强杀后记录永久卡在 processing ✅

`release_processing` 在强杀时不会执行，记录停在 `processing`，用户重试只会
拿到 `processing_stream`。接入启动时孤儿认领恢复——租约安全（排他 advisory
锁 vs 在线请求的共享锁），且任何异常都不阻断启动。

`app/governance/startup_recovery.py`

### #12 复核后判定为设计意图，未改动 ⬜

`PostgresPreferenceRepository.upsert` 的「只插不更新」看着像 bug，实际是
偏好确认的**审计轨迹**设计，由测试名 `..._is_add_only_...` 钉住，读侧
`resolve_preference_defaults` 按 `confirmed_at` 取最新一条。**这是我最初的
误判，代码本来是对的。**

## 四、架构：整套知识图谱是死代码

### #13 图谱检索在默认模式下从不被调用 ✅

**这一批里最严重的一项。**

`TRAVEL_AGENT_MODE` 默认是 `supervisor_subagents`，真实请求走
`app/agents/subagents/**`。但图谱检索只接在 `workers/attractions.py` 和
`hotel.py` 上——那是 `mode=supervisor` 的**旧路径**。

结果：整套 `graph_extraction`、`KnowledgeEntity`/`KnowledgeRelation` 两张表、
`GraphKnowledgeService`，在默认配置下**一条都不会被查到**。往图谱里灌多少
数据，对线上规划的影响都是零。

**接入方式上否掉了一个看起来更自然的做法**：不新增 `"graph"` provider 塞进
`provider_order`。那是**降级链**——`base.run` 里只要有 provider 报
`sufficient` 就 `break`，`local_rag` 一命中，排它后面的图谱永远轮不到；
排前面又会抢占文档检索。图谱和文档是**互补**不是备选，所以在 `local_rag`
provider 内部合并，语义跟旧路径的 `[*doc, *graph]` 保持一致。

图谱失败只降级为「没有图谱补充」，不把整个 provider 打成 `failed`——否则会
触发多余的 Deep Search 补搜。

`app/agents/subagents/tools.py`

### #14 search_related_entities 收了 query 却从不使用 ✅

返回整城**全部**关系，且无上界。这些关系在 `rag_analysis` 里会逐条变成
`CandidateOption` 拼进 LLM prompt——城市图谱一长起来就会把文档证据挤到
prompt 边缘，token 成本还随库线性上涨。

改为按实体名命中度排序 + 截断到 6 条（对齐文档侧 `HybridRetriever(k=4)`
的量级）。

**用排序而非硬过滤**：关系文本（`"A 位于 B"`）太短，词面过滤会让稀疏图谱
直接返回空。排序依据以 `graph_relevance` 落在 metadata 上，与文档侧
`rerank_score` 对称，便于排查召回问题。

`app/agents/workers/graph_knowledge.py`

## 六、MCP 可靠性层

这三个都是**跑起来探出来的，不是读代码看出来的**——尤其第一个，只在取消
时序下才显形。共同特征：上游越不稳越容易踩到。

### #16 失败的 inflight 任务不清理，把旧错误重放给后来者 ✅

`execute` 的 `finally` 只在 `existing.done()` 为真时才把任务从 `_inflight`
里摘掉。但等待方被取消时（SSE 断开、上层超时——都是常态），`finally` 跑的
那一刻被 `shield` 保护的任务往往还没结束，于是摘不掉；等它随后失败，就
**永久留在表里**。

下一个请同一个 key 的调用直接 `await` 这个早已失败的任务，拿到**上一次**的
错误——而目标服务此刻可能早就恢复了。探针验证：真正的操作 `called=False`，
一次都没执行过，也没有任何重试。

### #17 熔断器把新鲜缓存一起挡掉了 ✅

缓存的意义恰恰是上游挂掉时还能答上来，而 `_check_circuit` 在读缓存之前。
更糟的是熔断器是**全局**的：查天气失败三次，会让另一个 key 上完全健康、
缓存还新鲜的搜索结果一起被拒。

改为先查缓存再查熔断。同时有测试钉住「这不能变成绕过」——没有缓存时熔断
必须照旧拦住新的出网请求。

### #18 缓存只增不减 ✅

过期条目从不回收，也没有条目上限。`search` 的 `cache_key` 里带**完整 query
文本**（`tavily:{query}:{max_results}`），用户输入的多样性直接变成常驻内存。

加条目上限（512），优先淘汰过期项，再按最早到期淘汰。不做「过期即刻回收」
——每次写缓存都全量扫一遍 dict 是请求路径上的 O(n)，内存的真正保证来自上限。

`app/mcp_core/reliability.py`

## 方法

每处修复都是**先写失败测试 → 确认它对旧代码失败 → 改代码 → 确认转绿**，
然后做**变异测试**：故意把修复破坏掉，确认有测试挂，再逐字节还原。

这一轮变异测试抓到一个测试套自身的洞：缓存淘汰顺序的变异**存活了**——
过期项一清就已经降到上限以下，排序淘汰那条分支根本没走到。补了一个
「全存活条目超上限」的用例才盖住。
