# 旅行主 Agent 路由与规划工具设计

## 目标

将项目重构为以主 Agent 为唯一对话入口的工具调用架构。主 Agent 每轮根据当前消息和对话上下文判断用户意图，并在需要时调用旅行表单、目的地推荐 RAG、开放问答 RAG 或旅行规划 Supervisor。系统不再依据历史槽位自动进入规划，也不再用默认日期或默认天数直接生成行程。

## 核心角色

### 主 Agent

主 Agent 负责所有用户对话和意图判断，但不直接执行完整旅行研究。它可以：

- 直接处理普通对话。
- 调用开放问答 RAG 工具。
- 调用目的地推荐 RAG 工具。
- 调用旅行信息表单工具。
- 在表单结果完整后调用 Supervisor 工具。
- 接收工具结果并组织最终用户回复。

主 Agent 每轮重新判断意图。会话中已经存在目的地或旧行程，不得阻止当前消息进入开放问答路径。

### 旅行信息表单工具

表单是由主 Agent 调用的前端工具，不是普通聊天消息，也不是后端根据缺失槽位自动弹出的固定界面。

表单包含三个必填步骤：

1. 目的地。
2. 出发日期。
3. 旅行天数，范围为 1 至 30 天。

用户完成后，前端将结构化结果作为 Tool Result 返回主 Agent。只有三个字段全部有效时，主 Agent 才能调用 Supervisor。系统不得使用默认日期或默认天数绕过确认。

如果用户在提出规划请求时已经说出部分信息，主 Agent调用表单时应将这些信息作为预填值。例如“帮我规划一次成都旅行”会预填目的地为成都。

### Supervisor

Supervisor 只处理已经确认且字段完整的旅行规划请求。它负责：

- 根据结构化需求创建研究任务。
- 调用五类专业 Worker。
- 检查各 Worker 的状态、证据和警告。
- 汇总研究结果并编排完整行程。
- 将结构化行程返回主 Agent。

Supervisor 不直接与用户对话，也不负责决定是否弹出表单。

### 专业 Worker

规划阶段包含五类 Worker：

- 景点 Worker。
- 天气 Worker。
- 交通 Worker。
- 住宿 Worker。
- 美食 Worker。

每个 Worker 的具体 RAG、外部搜索或 API 数据来源暂不在本设计中确定，后续单独设计。当前只确定职责边界和 Supervisor 调用关系。

## 新会话流程

每次新建会话后，主 Agent 主动发送：

> 需要我帮你规划一下旅行吗？

这条消息建立确认规划的上下文。用户回复“好的”“可以”等肯定语句时，主 Agent 将其识别为规划意图并调用旅行信息表单工具。

如果用户不等待询问，直接提出“帮我规划一次成都旅行”等明确规划请求，主 Agent 同样立即调用表单，并预填已识别字段。

## 意图路由

```text
用户消息
  -> 主 Agent 判断本轮意图
     -> 明确规划或确认规划
        -> 调用旅行信息表单工具
        -> 收到完整 Tool Result
        -> 调用 Supervisor 工具
        -> 收到结构化行程
        -> 主 Agent 回复用户
     -> 目的地未确定并请求推荐
        -> 调用目的地推荐 RAG
        -> 主 Agent 给出候选城市
        -> 用户选定城市
        -> 恢复旅行信息表单
     -> 开放式旅行问题
        -> 调用开放问答 RAG
        -> 主 Agent 组织并直接回复
     -> 普通对话或拒绝规划
        -> 主 Agent 直接回复或等待后续需求
```

## 开放问答规则

“最近成都有什么好玩的？”等开放式问题直接走主 Agent 到 RAG 的路径：

- 不弹出旅行表单。
- 不调用 Supervisor。
- 不因为历史会话存在目的地或行程而改变路由。
- 回答结束后不再次自动追问是否需要规划。
- 只有用户后来明确提出规划时才进入表单流程。

## 目的地未确定

目的地步骤提供“帮我推荐”选项。用户选择后：

1. 暂停并保留当前表单状态。
2. 主 Agent 调用目的地推荐 RAG。
3. 主 Agent 返回候选城市。
4. 用户选择或输入一个目的地。
5. 恢复原表单，继续填写日期和天数。

目的地未确认前不得调用 Supervisor。

## 工具调用契约

### 表单调用

主 Agent 发出结构化工具调用，至少包含：

```json
{
  "tool": "collect_trip_requirements",
  "call_id": "unique-call-id",
  "arguments": {
    "initial_values": {
      "destination": "成都"
    }
  }
}
```

前端根据工具名称显示三步表单。关闭表单、填写中和提交中都属于该工具调用的状态，不应伪装成用户聊天消息。

### 表单结果

```json
{
  "tool": "collect_trip_requirements",
  "call_id": "unique-call-id",
  "status": "completed",
  "result": {
    "destination": "成都",
    "departure_date": "2026-08-10",
    "days": 4
  }
}
```

`call_id` 用于关联调用与结果，并防止重复提交。后端必须重新校验日期、天数和文本长度。

### Supervisor 调用

主 Agent 在收到有效表单结果后调用 Supervisor，参数只使用已经确认的结构化数据。Supervisor 返回完整结构化行程和各 Worker 的状态摘要，主 Agent 再生成面向用户的最终回答。

## 状态与持久化

会话需要分别保存：

- 用户和主 Agent 的聊天消息。
- 主 Agent 的工具调用。
- 工具结果。
- 未完成表单的当前步骤和字段值。
- Supervisor 任务和 Worker 事件。
- 已生成的结构化行程。

切换会话或刷新页面后，前端根据持久化工具调用恢复未完成表单。聊天历史不得丢失工具调用与结果之间的关系。

## 明确废弃的现有行为

- 目的地一旦存在就自动进入规划或改写。
- 只有目的地缺失时才判断开放问答。
- 缺少日期时自动使用七天后。
- 缺少天数时自动使用三天。
- 用关键词直接决定重跑某个 Worker。
- 把快捷选项点击结果作为普通聊天消息提交。
- 将表单视为后端缺失字段追问，而不是主 Agent 工具调用。

## 错误处理

- 表单校验失败时保留用户已填内容并显示字段错误。
- 同一个 `call_id` 只能成功提交一次。
- Supervisor 失败时主 Agent 返回明确错误，不伪造行程。
- 单个 Worker 失败时 Supervisor 标记部分完成，并决定结果是否足以形成安全的行程草稿。
- RAG 无结果时主 Agent明确说明资料不足，不自动切换到 Supervisor。

## 测试范围

- 新会话主动询问是否规划。
- 肯定回复触发表单工具。
- 明确规划请求直接触发表单并预填字段。
- 开放问题只调用 RAG。
- 历史目的地不影响当前开放问答路由。
- 三个表单字段全部必填且不使用默认值。
- 目的地推荐后恢复原表单。
- Tool Call 与 Tool Result 通过 `call_id` 正确关联。
- 完整表单结果才允许调用 Supervisor。
- Supervisor 调用五类 Worker 并将结果返回主 Agent。
- 刷新和切换会话后恢复未完成工具状态。
